# Secrets setup — step by step (SEC)

## Part 1: your dev VM (about 15 minutes)
1. Copy this kit into your clone of the repo (paths as in README.md) and commit it on a branch.
2. `bash scripts/setup-dev-secrets.sh`
   Installs git, ansible, pre-commit and creates `~/.jengasec/vault-platform` and `vault-ci` (random, mode 600).
3. **Put both vault passwords in the password manager now.** Open the files locally; never paste them into chat or a ticket.
4. Create the real vault file (needs the `ansible/` directory as the working dir, so ansible.cfg is found):
   `cd ansible && ansible-vault create --encrypt-vault-id platform group_vars/all/vault.yml`
   Add the keys from `vault.yml.example` with real values, save, then confirm: `head -1 group_vars/all/vault.yml` starts with `$ANSIBLE_VAULT;`.
5. `pre-commit install && pre-commit run --all-files` (first run needs internet to fetch gitleaks).
6. Prove the guards work (checks C1-C3 in test-run-plan.md):
   - add a fake token such as `ghp_` + 36 random letters to a scratch file and try to commit it: blocked.
   - try to commit a plaintext `vault.yml`: blocked.
   - `ansible-vault view group_vars/all/vault.yml` works; with the password file moved away it fails.
7. Add the CI check (same script) when the repo has CI, and append `gitignore-additions.txt` to `.gitignore`.
8. Open the PR; ask Platform and APP to confirm owners and rotation in `docs/secrets.md`.

## Part 2: the shared VM (runtime secrets) — with Platform
1. As root on the shared VM: `./setup-runtime-secrets.sh <platform-user> <app-user>` (only people who truly need to read secrets).
2. Add each secret with `sudo jengasec-put-secret NAME` (value from stdin, so it never appears in argv or shell history).
3. Services read them from `/etc/jengasec/secrets/NAME` (or load via systemd `LoadCredential=`). They never go in environment files in the repo.
4. Optional audit trail (the shared VM already holds the audit log): `auditctl -w /etc/jengasec/secrets -p rwa -k jengasec-secrets`, made permanent in `/etc/audit/rules.d/`.
5. Back up with Platform's backups to Server 1 **only encrypted**.

## Part 3: kubernetes secrets (with APP)
- Per-cell database passwords are generated by the cell chart as Kubernetes Secrets, one per namespace, never shared across cells and never copied into logs.
- Restrict the deploy role so pods cannot read Secrets in other namespaces (SEC-02 RBAC).

## Part 4: decisions needed (bring to Cristine and Platform)
1. **Password manager.** Which one, who administers it, and where it is hosted. Without one, the "share in person or through the password manager" rule has no tool behind it.
2. **Named Tier 0 members**: Platform lead, you, one backup.
3. **Retirement date** for the shared bootstrap login.
4. **WireGuard keys**: generated by each participant (recommended) or by the server.
5. **Retention**: when participant pull tokens and per-person attribution data are deleted.
